PROJECT: NOTICIARIO

## 1. PROJECT OVERVIEW

Project name: Noticiario.

Goal:
Noticiario is a Laravel 12 + Inertia + React + TypeScript platform for creating short digital news bulletins from editorial planning to production-ready scripts.

High-level workflow:
1. Configure bulletin/schedule.
2. Create run.
3. Generate prompt.
4. Generate or paste AI response.
5. Parse response.
6. Create script.
7. Review/fact-check.
8. Verify sources.
9. Approve script.
10. Prepare production metadata.
11. Later audio/video/publishing.

Architecture:
- Laravel 12
- Inertia
- React
- TypeScript
- Tailwind
- MySQL
- Spatie Laravel Permission

Restrictions:
- No Blade application pages.
- resources/views/app.blade.php is only the Inertia root view.
- React pages live in resources/js/Pages.
- React layouts live in resources/js/Layouts.

## 6. TRANSLATION RULE

Strict translation policy:
- UI translations live in resources/js/i18n/translations.ts.
- Active UI locales:
  - en
  - es
  - fr
- All visible React UI strings must use useTranslations().t().
- Status/enum values must be mapped to translated labels.
- Flash messages should be translatable keys where practical.
- Database-backed visible content should include translations where supported.
- Prompt templates should be language-specific where supported.

Mandatory future branch rule:
Every branch that adds or changes visible UI text must update:
- resources/js/i18n/translations.ts
- English, Spanish and French keys
- database seed translations if content is database-backed
- prompt templates in the correct language if templates/prompts are added

No new visible English-only text should be merged.

## 7. DOCUMENTATION UPDATE RULE

Every future branch must update doc.txt by doing BOTH:

Do not only append new sections.

## 9. CURRENT ROADMAP

1. feature/ai-logs-cost-control-advanced
- Objective: add cost-control policies, usage limits, and richer AI log observability.
- Expected result: safer operational AI usage and clearer financial oversight.
- Why this order: it improves reliability and control before automation layers depend on AI volume.

2. feature/automatic-schedule-runner
- Objective: execute eligible editorial schedules automatically.
- Expected result: schedule runs created/executed without manual trigger for supported modes.
- Why this order: automation should start only after tighter AI usage controls are in place.

3. feature/queue-worker-foundation
- Objective: introduce queue infrastructure for asynchronous editorial pipeline jobs.
- Expected result: background execution foundation for scalable workflow steps.
- Why this order: schedule automation and media steps need queue primitives to scale safely.

4. feature/audio-production-foundation
- Objective: define base audio production pipeline for approved scripts.
- Expected result: scripts can progress into structured audio generation stages.
- Why this order: comes after automation/queue groundwork to avoid fragile synchronous processing.

5. feature/video-production-foundation
- Objective: define base video production pipeline aligned with script and metadata outputs.
- Expected result: approved content can move into structured video generation stages.
- Why this order: video builds on metadata and pipeline capabilities established by earlier steps.

6. feature/publishing-foundation
- Objective: implement publishing domain model and initial destination connectors.
- Expected result: internal publication records and initial outbound publishing workflow.
- Why this order: publishing should start once audio/video artifact pipelines exist.

7. feature/public-viewer-content-and-search
- Objective: improve public/viewer exploration with richer content discovery.
- Expected result: broader public browsing and searchable published bulletin history.
- Why this order: it depends on stabilized publishing and persisted publication outputs.

8. feature/media-picker-and-assets
- Objective: add reusable media picker, asset association UX, and richer media tooling.
- Expected result: faster editorial/media reuse and stronger production asset management.
- Why this order: best introduced after core publication content types are established.

9. feature/live-source-checking-optional
- Objective: provide optional live URL/source checks without replacing manual verification.
- Expected result: editor-assist verification signals while preserving manual final judgment.
- Why this order: optional enrichment can be layered after core editorial/publishing stability.

10. feature/privacy-consent-and-public-seo-hardening
- Objective: harden public compliance and SEO/privacy behavior.
- Expected result: stronger production-grade public controls and safer analytics/search indexing posture.
- Why this order: final hardening step once public surface and publishing flows are stable.
